### Deviations from the brief's script text

1. **`a.ticket-card` → `a.ticket-card__link`.** The brief's selector for the first ticket card link (`page.locator('a.ticket-card').first()`) never matches: `TicketCard` renders `<article class="ticket-card ticket-card--{kind}">` (not a link) containing `<a class="ticket-card__link">`. Fixed to `a.ticket-card__link` so the ticket/place screenshots are actually produced instead of silently skipped.
2. **Ticket/place deep links carry `?trip=`.** `/ticket/:trip/:id` and `/place/:id` read their data from the app-wide trip context (`useTrip()`), not from the `:trip` path segment. On a genuinely fresh full-page load (exactly what `page.goto` does) with no `?trip=` in the query string, `resolveSlug()` falls back to `defaultSlug()` (today's trip, else `trips[0]`) rather than the trip the link came from. Confirmed this is a real gap, not just a probe artifact — see Finding 1 below. Fixed the probe by appending `?trip=${trip}` to the extracted `href` before navigating, so the ticket/place screenshots reflect the intended city.

Both fixes are one-line changes inside `tools/probe-screens.mjs` only; no application code was touched for either.

## Findings for the controller

1. **Deep-link trip context (app behavior, not fixed here).** `TicketDetail`/`PlaceDetail` resolve their data from `useTrip()`'s ambient trip context, not from the `:trip` path segment in their own route. Client-side (in-app) navigation is unaffected because the trip context is already loaded and persists across route changes. But a cold full-page load of `/ticket/<trip>/<id>` or `/place/<id>` with no `?trip=` in the URL (e.g. a bookmarked/shared link, or a hard refresh while on that screen) silently resolves the *wrong* trip — today it would 404 into whichever trip is chronologically first (`trips[0]`) or matches "today" — and shows "No ticket … in <wrong city>." Reproduced directly: `GET /ticket/seville/T04` cold gave "No ticket T04 in Lisbon." This is worth a real fix (e.g. have the route call `setSlug(tripParam)` on mount when it differs) but is out of scope for Task 9's screenshot tooling.
2. **Lisbon map over-zooms.** `/map/2026-10-01?trip=lisbon` renders zoomed out to show all of Portugal north of Lisbon (see `lisbon-map.png`, pin "11" up near Turcifal) instead of a tight fit on the day's stops in central Lisbon/Belém. One imported stop almost certainly has bad or missing lat/lng, dragging the auto-fit bounds out. Likely a `content/lisbon` import data problem, not a code bug — flagging for the controller/import step, not fixed here.
3. **First-ticket auto-pick is event-kind in both cities.** The brief's "first ticket card" pick (`Tickets` screen, first `<a class="ticket-card__link">`) happens to be a restaurant/event booking in both Seville (`La Chunga`) and Lisbon (`Mesa de Frades`), so `seville-ticket.png`/the Lisbon ticket render the **event-detail hero layout**, not the three-part boarding pass. Manually verified the boarding-pass layout separately against a real transport booking (`GET /ticket/seville/T04`, the AVE Seville→Barcelona train) — route ends, glyph, dotted mid-section, booking/ref cells, priority, and stub with status all render correctly. Included that extra screenshot as `seville-ticket-pass.png` so the owner can see both ticket layouts.
4. **`fullPage: true` screenshots interleave the fixed tab bar mid-page.** Because the tab bar is `position: fixed`, a full-page screenshot (used for Home/Day/Tickets/More/ticket/place) captures it wherever the viewport happened to be when the screenshot API stitches the page, so it appears to overlap content partway down several screenshots (e.g. `lisbon-home.png`'s Reminders section). This is a Playwright full-page-screenshot artifact, not a rendering bug in the live app — noting it so the owner isn't alarmed by an apparent overlap.
